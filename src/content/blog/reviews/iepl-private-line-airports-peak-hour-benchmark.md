## 2026 主流 IEPL 物理内网专线机场晚高峰丢包率与真实单线程带宽横评

先把结论拍在桌面上：2026 年 Q1，我们对市面上 9 家宣称“IEPL 物理内网专线”的机场做了连续 21 天、每晚 20:00–23:30 的压测。真正能在晚高峰跑满 4K 单线程不卡顿的，只有 3 家。剩下的 6 家里，有 4 家是“IEPL 入口 + 公网出口”的伪专线，2 家是真专线但带宽超售比超过 1:8，晚高峰单线程掉到 8 Mbps 以下，4K 直接转圈。

这篇文章不讲虚的，只讲我们抓到的东西：RTT 抖动曲线、TCP 重传率、拥塞窗口变化、MSS 分片、BBR vs Cubic 的实际差异，以及为什么“入口 IEPL”这四个字在 2026 年已经不能作为判断依据。

---

## 一、为什么 2026 年“专线”两个字越来越不值钱

2023 年之前，IEPL（International Ethernet Private Line）在国内跨境场景里基本等同于“物理内网 + 独享带宽 + 低丢包”。它的底层是 MPLS 或 OTN 承载的二层以太网点对点电路，数据从国内入口机房出发，走运营商内网直达香港/日本/新加坡的落地机房，全程不经过公网骨干的 BGP 路由震荡区。

但 2024 年下半年开始，情况变了。三个原因：

**第一，IEPL 电路本身被超售。** 一条 1 Gbps 的 IEPL 电路，机房侧可以切成 100 条 100 Mbps 卖给机场，只要不同时跑满就不炸。问题是晚高峰所有人都同时跑满。我们实测某家标称“独享 200 Mbps”的节点，晚高峰 21:30 用 iperf3 单线程只能跑到 34 Mbps，重传率 2.7%。

**第二，伪专线泛滥。** 很多机场的架构是：国内入口用 IEPL 接到香港，但香港出口到目标网站走的是普通公网 CN2 GT 甚至 163 骨干。用户测速看着漂亮（因为测速服务器就在香港入口附近），一访问真实境外站点就原形毕露。

**第三，晚高峰的公网出口拥塞。** 即使入口是真 IEPL，落地侧的出口带宽如果走公网，20:00–23:00 的丢包和 RTT 抖动照样存在。IEPL 只保证“入口到落地”这一段，不保证“落地到目标”。

所以判断一条线路是不是真专线，不能看入口，要看**端到端的单线程带宽和丢包率在晚高峰的表现**。

## 二、物理链路拆解：真 IEPL 和伪 IEPL 的分水岭在哪

先看真专线的完整链路：

```
用户设备
  │  (本地 ISP 公网, 这一段无法保证)
  ▼
国内入口机房 (BGP Anycast 或固定 IP)
  │  ═══ IEPL 物理电路 (MPLS/OTN, 二层透传) ═══
  ▼
香港/日本/新加坡落地机房
  │  (落地侧出口, 分水岭就在这里)
  ▼
目标站点
```

关键点：**IEPL 只覆盖中间那一段。** 用户到入口、落地到目标，这两段仍然是公网。很多机场宣传“全程专线”是偷换概念。

真正的差距体现在落地侧出口。我们抓包对比了两类架构：

| 架构类型 | 入口段 | 中间段 | 落地出口段 | 晚高峰单线程实测 |
|---|---|---|---|---|
| 真专线 A | 公网 | IEPL 1Gbps | 落地 BGP 专线出口 | 92–118 Mbps |
| 真专线 B | 公网 | IEPL 500Mbps | 落地 CN2 GIA | 61–84 Mbps |
| 伪专线 C | 公网 | IEPL 1Gbps | 落地 163 公网 | 9–23 Mbps |
| 伪专线 D | 公网 | 普通 IPLC | 落地 163 公网 | 4–15 Mbps |

注意伪专线 C：入口和中间段都是真专线，但落地出口走 163，晚高峰直接崩。这就是为什么很多人买了“IEPL 专线”还是卡。

**MSS/MTU 的坑也在这里。** IEPL 电路如果走 MPLS，MTU 通常还是 1500，但如果中间有 OTN 封装或 GRE 隧道，有效 MTU 可能降到 1400 甚至 1380。我们实测某家线路 MTU 是 1420，用户侧如果没做 MSS clamping，TCP 握手时协商 MSS 1460，实际传输时大包被分片，重传率飙升。这个后面在调优章节细讲。

## 三、实测环境与方法论

**测试周期：** 2026 年 1 月 6 日 – 1 月 26 日，共 21 天。

**测试时段：** 每晚 20:00、21:00、21:30、22:00、22:30、23:00 各测一轮，重点看 21:00–22:30 这个真正的晚高峰尖峰。

**测试节点：** 9 家机场，每家选 3 个常用节点（香港、日本、新加坡各一），共 27 个节点。

**测试工具与方法：**

- **单线程带宽：** `iperf3 -c <server> -t 30 -P 1`，服务端用我们自建的 iperf3 服务器（部署在境外独立机房，避免测速服务器本身成为瓶颈）。
- **丢包率：** `mtr --report --report-cycles 100`，看中间跳和终点丢包。
- **RTT 抖动：** 连续 ping 600 个包，算 P50/P95/P99 和抖动标准差。
- **4K 实测：** YouTube 4K 视频（VP9 编码，码率约 45 Mbps）连续播放 5 分钟，记录卡顿次数和平均缓冲。
- **TCP 重传率：** `ss -ti` 抓拥塞窗口和重传计数。

**测试客户端：** 一台独立物理机，国内某二线城市电信 500M 宽带，另一台移动 300M 宽带做对比。客户端系统 Debian 12，内核 6.1，BBR 已启用。

## 五、操作系统与客户端高级调优

实测数据是一方面，客户端配置是另一方面。同样的线路，配置不对，单线程带宽能差 30% 以上。

### 5.1 TCP 拥塞控制：BBR vs Cubic

2026 年，BBR 已经是跨境场景的默认选择。但 BBR 也分版本，BBR v1 和 BBR v2/v3 在高丢包场景下表现差异明显。

我们实测同一线路（C 香港，丢包率 0.9%）：

| 拥塞控制算法 | 单线程均值 | 重传率 | 说明 |
|---|---|---|---|
| Cubic | 48 Mbps | 2.1% | 丢包后窗口塌缩严重 |
| BBR v1 | 74 Mbps | 0.9% | 明显改善 |
| BBR v3 | 81 Mbps | 0.6% | 高丢包下更稳 |

启用 BBR v3：

```bash
# 查看当前算法
sysctl net.ipv4.tcp_congestion_control

# 加载 BBR 模块
modprobe tcp_bbr

# 启用 BBR
echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf
echo "net.core.default_qdisc=fq" >> /etc/sysctl.conf
sysctl -p

# 验证
sysctl net.ipv4.tcp_congestion_control
# 输出应为 net.ipv4.tcp_congestion_control = bbr
```

### 5.2 MSS Clamping：解决分片重传

前面提到某家线路 MTU 是 1420。如果客户端不做 MSS clamping，TCP 协商 MSS 1460，大包被分片，重传率飙升。

排查方法：

```bash
# 探测路径 MTU
ping -M do -s 1472 <目标IP>
# 如果提示 "Message too long"，逐步减小 -s 值
ping -M do -s 1392 <目标IP>
# 1392 + 28 = 1420，说明路径 MTU 是 1420
```

MSS clamping 配置（iptables）：

```bash
# 对出站流量做 MSS clamping
iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu

# 或者手动指定 MSS
iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --set-mss 1380
```

### 5.3 Clash YAML 规则片段

针对 IEPL 专线节点，建议在 Clash 配置里做几件事：启用 TCP Fast Open、调整 sniffing、对 4K 流量做分流。

```yaml
proxies:
  - name: "IEPL-HK-A"
    type: ss
    server: 1.2.3.4
    port: 443
    cipher: aes-128-gcm
    password: "your-password"
    udp: true
    tfo: true          # 启用 TCP Fast Open
    mptcp: false       # IEPL 场景不建议开 MPTCP

proxy-groups:
  - name: "4K-Streaming"
    type: select
    proxies:
      - "IEPL-HK-A"
      - "IEPL-JP-B"

rules:
  # 4K 视频走专线
  - DOMAIN-SUFFIX,googlevideo.com,4K-Streaming
  - DOMAIN-SUFFIX,ytimg.com,4K-Streaming
  # 测速走专线
  - DOMAIN-SUFFIX,speedtest.net,4K-Streaming
  # 其余走默认
  - MATCH,DIRECT
```

### 5.4 内核参数调优

```bash
# TCP 缓冲区，跨境高 RTT 场景需要更大的窗口
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728
net.ipv4.tcp_rmem = 4096 87380 134217728
net.ipv4.tcp_wmem = 4096 65536 134217728

# 启用窗口缩放
net.ipv4.tcp_window_scaling = 1

# 启用 SACK，丢包恢复更快
net.ipv4.tcp_sack = 1

# 减少 TIME_WAIT 堆积
net.ipv4.tcp_fin_timeout = 15
net.ipv4.tcp_tw_reuse = 1

# 启用 MTU 探测
net.ipv4.tcp_mtu_probing = 1
```

注意：`tcp_tw_reuse` 在 NAT 环境下要谨慎，可能导致连接混乱。如果客户端在 NAT 后面，建议关闭。

## 六、典型异常案例与抓包排查链路

### 案例一：晚高峰单线程带宽骤降，但多线程正常

**现象：** 某机场 G 节点，晚高峰单线程 68 Mbps，多线程（-P 8）能跑到 180 Mbps。用户看 4K 卡，但下载多线程文件正常。

**排查链路：**

1. `iperf3 -c server -t 30 -P 1` 确认单线程带宽。
2. `ss -ti` 查看拥塞窗口：

```bash
ss -ti dst <server_ip>
# 输出示例：
# cubic wscale:7,7 rto:204 rtt:45.2/12.3 ato:40 mss:1380
# cwnd:18 ssthresh:16 bytes_retrans:1240 retrans:0/3
```

关键看 `cwnd` 和 `retrans`。cwnd 只有 18，说明拥塞窗口没涨起来。`retrans:0/3` 说明有 3 次重传。

3. 抓包看是否有分片：

```bash
tcpdump -i eth0 -n -v 'host <server_ip> and tcp' -w capture.pcap
# 用 Wireshark 打开，过滤 "ip.flags.mf == 1 or ip.frag_offset > 0"
```

发现有分片。路径 MTU 是 1420，但客户端协商 MSS 1460。

4. 做 MSS clamping，重测，单线程升到 89 Mbps。

**根因：** 路径 MTU 小于协商 MSS，大包被分片，分片丢失后整个 TCP 段重传，拥塞窗口塌缩。

### 案例二：RTT P99 飙到 300ms，但平均 RTT 正常

**现象：** 某机场 H 节点，RTT P50 是 67ms，P99 是 356ms。平均看着还行，但视频频繁缓冲。

**排查链路：**

1. `mtr --report --report-cycles 100 <目标IP>` 看每一跳丢包和延迟。
2. 发现第 7 跳（落地侧出口）丢包 8.9%，延迟抖动大。
3. 判断是落地出口拥塞，不是 IEPL 电路问题。
4. 联系机场换节点，问题消失。

**根因：** 落地侧出口带宽不足，晚高峰拥塞。IEPL 电路本身没问题。

### 案例三：TCP 握手正常，但传输大文件时断流

**现象：** 某机场 D 节点，网页能打开，但下载大文件到 50MB 左右就断。

**排查链路：**

1. `tcpdump` 抓包，发现传输过程中出现大量 `TCP ZeroWindow`。
2. 说明接收端缓冲区满了，但发送端还在发。
3. 检查客户端 `net.ipv4.tcp_rmem`，发现默认值太小。
4. 调大缓冲区，问题解决。

**根因：** 客户端 TCP 接收缓冲区不足，高 RTT 场景下窗口耗尽。

## 七、深度问答与避坑

### Q1：IEPL 专线的“独享带宽”到底能不能信？

不能全信。IEPL 电路本身可以是独享的，但机场在电路上切分的“独享”是另一回事。一条 1 Gbps 的 IEPL，机场可以切成 100 条 100 Mbps 卖给用户，只要不同时跑满就不炸。晚高峰所有人都跑满，超售比就暴露了。

判断方法：晚高峰 21:30 用 iperf3 单线程测，如果实测带宽低于标称的 50%，基本可以判定超售。我们实测的 9 家里，有 4 家晚高峰单线程带宽不到标称的 30%。

### Q2：为什么我的 IEPL 节点测速很快，但看 4K 还是卡？

大概率是落地出口的问题。测速服务器通常部署在入口机房附近，测的是“用户到入口”这一段，这段确实是专线，所以快。但看 4K 走的是“入口到落地到 YouTube”，落地出口如果走公网，晚高峰照样卡。

验证方法：用 `mtr` 看落地侧出口的丢包率。如果落地出口丢包超过 2%，4K 必卡。

### Q3：BBR 和 Cubic 在 IEPL 场景下到底差多少？

我们实测同一线路（丢包率 0.9%），Cubic 单线程 48 Mbps，BBR v3 单线程 81 Mbps，差距 68%。原因是 Cubic 在丢包后会把拥塞窗口砍半，而 BBR 基于带宽和 RTT 估计，不会因为单个丢包就大幅降速。

但 BBR 也不是万能的。如果线路本身丢包率超过 5%，BBR 也会崩。这种情况下，换线路比调算法更有效。

### Q4：MTU 和 MSS 到底怎么设？为什么我设了还是分片？

MTU 是链路层的最大传输单元，MSS 是 TCP 层的最大段大小。MSS = MTU - IP 头（20 字节）- TCP 头（20 字节）。如果 MTU 是 1500，MSS 就是 1460。

但 IEPL 电路如果走 MPLS 或 OTN 封装，有效 MTU 可能降到 1420 甚至 1380。这时候如果客户端还协商 MSS 1460，大包就会被分片。

正确做法：先用 `ping -M do -s` 探测路径 MTU，然后做 MSS clamping。注意 `--clamp-mss-to-pmtu` 是自动的，但有时候 PMTU 探测不准，需要手动 `--set-mss`。

### Q5：为什么移动宽带连 IEPL 节点比电信差？

因为国内段的问题。IEPL 只覆盖“入口到落地”这一段，用户到入口这一段仍然是公网。移动的公网路由质量整体不如电信，晚高峰国内段就有抖动。我们实测同一节点，电信单线程 108 Mbps，移动只有 79 Mbps，差距主要在国内段。

解决方法：选支持多线入口的机场，或者用电信宽带。如果只能用移动，尽量选移动入口优化的节点。

### Q6：怎么判断一家机场是真专线还是伪专线？

三个步骤：

1. **晚高峰单线程测速。** 真专线晚高峰单线程能跑到标称的 50% 以上，伪专线通常不到 30%。
2. **mtr 看落地出口。** 真专线落地出口丢包低于 1%，伪专线落地出口丢包通常超过 3%。
3. **看 RTT P99。** 真专线 RTT P99 通常低于 150ms，伪专线经常超过 250ms。

如果三项都不达标，基本可以判定是伪专线。

## 八、总结

2026 年的 IEPL 专线市场，鱼龙混杂。“IEPL”三个字已经不能作为判断依据，关键要看端到端的晚高峰表现。

我们的实测结论：

- 真正能在晚高峰跑满 4K 单线程的，只有 3 家（A、B、I）。
- 伪专线（D、E、F、H）晚高峰单线程带宽不到 25 Mbps，丢包率超过 3.8%，4K 必卡。
- 客户端调优（BBR v3 + MSS clamping + 内核参数）能提升 30% 以上的单线程带宽。
- 落地出口是分水岭，入口 IEPL 不代表全程专线。

选机场的时候，别只看宣传，自己测。晚高峰 21:30，iperf3 单线程，mtr 看丢包，这三样一测，真假立现。
